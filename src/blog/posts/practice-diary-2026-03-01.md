# 从可记录到可教学：知识棱镜与 Agent-First 架构的融合实践

> Day 30 · 2026-03-01

今天的主线任务是将 `js-knowledge-prism` 项目从简单的"CLI + Plugin"结构升级为完整的 Agent-First 五层架构，旨在解决随着素材规模增长，原有时间线笔记难以转化为结构化知识，且缺乏自动化分发与安全执行机制的瓶颈。

## 构建"Journal-Pyramid-Outputs"三层蒸馏架构

面对日益增长的笔记素材，我深刻意识到仅靠日期归档的 `journal` 层只能回答“那天学了什么”，却无法支撑“关于 X 话题我知道什么”的结构化查询。为此，我严格确立了三层架构：`journal` 层忠实记录原始素材，写完即归档不回头修改；`pyramid` 层作为核心引擎，通过自下而上的 Atoms 拆解与 Groups 归组，以及自上而下的 SCQA 序言设计与 Tree 展开，将碎片信息蒸馏为结构化观点；`outputs` 层则面向特定读者产出成品文章。这种关注点分离的设计确保了单层改动（如新增一篇笔记）不会波及整体体系，让知识从“可记录”真正走向“可复用”。

## 实施自下而上拆解与自上而下验证的双向轨道

在具体的知识处理流水线中，我实践了双向轨道的增量演化工作流。自下而上轨道将新输入的笔记拆解为独立的 Atoms，跨文档边界归组为 Groups 并提炼观点句，最终收敛为 Synthesis 候选；与此同时，自上而下轨道利用 SCQA 模型设计序言，展开金字塔全树并进行 MECE 验证。这种机制确保了每次新输入都经过完整的处理管线，知识体系在使用中自然生长而非一步到位。例如，同一批分析结果（analysis）作为公共素材池，可以支撑不同视角的 outputs（如教程或博客），实现了知识资产的高效复用。

## 确立 Agent-First 五层架构模式

为了解决工具调用与项目能力暴露的结构性问题，我参考 JS-Eyes 项目，将 `js-knowledge-prism` 重构为以 AI Agent 为第一消费者的五层架构。Layer 1（Agent 接口层）通过 `register(api)` 暴露 Tools、Services 和 CLI 三种原语，其中 Tool 的描述专门写给 LLM 看，参数严格遵循 JSON Schema；Layer 2（业务核心层）保持零框架依赖，确保核心逻辑可被 Plugin、CLI 及测试多方复用；Layer 3 独立为人类 CLI；Layer 4 和 Layer 5 则分别负责开发工具链与扩展技能生态。这次重构中最令我满意的是，所有新增能力都是围绕核心层“长出来的”，核心层代码（`lib/*.mjs`）实现了零改动。

## 打造全链路自动化开发工具链与技能生态闭环

为了实现无人值守的知识产出与分发，我新建了 Layer 4 开发工具链（`cli/cli.cjs`），支持 `build`、`bump`、`commit`、`sync`、`release` 五个命令。在实施过程中踩了一个坑：由于项目 `package.json` 设置了 `"type": "module"`，最初创建的 `.js` 开发脚本被当成 ESM 处理导致 `require()` 报错，最终通过将开发 CLI 文件统一改为 `.cjs` 扩展名解决了冲突。此外，我构建了 Layer 5 扩展技能体系，创建了第一个子技能 `skills/prism-output-blog/`，并通过 `SKILL.md` 作为技能“身份证”，让构建系统自动生成 `skills.json` 静态注册表。现在，Agent 可以自行发现、评估并安装所需技能，配合一键安装脚本，真正实现了从代码提交到技能上线的自动化闭环。

## 今天的收获

- **架构分层分离是演进基石**：通过将核心逻辑（Layer 2）与接口层（Layer 1/3）彻底解耦，确保了在增加自动化构建和扩展技能时，核心业务逻辑无需任何改动，验证了“核心逻辑写一次”的理念。
- **开发工具链需适配模块系统**：在 ESM 项目中开发内部 CLI 时，务必注意文件扩展名（`.cjs` vs `.js`）以避免模块解析冲突，这是保证构建流程顺畅的关键细节。
- **静态注册表驱动生态自生长**：技能注册表（`skills.json`）采用构建时生成的静态 JSON 而非动态 API，不仅降低了部署复杂度（可托管于任意静态站），还让 Agent 能够无服务端依赖地自主发现与安装技能。
- **双向轨道保障知识持续蒸馏**：坚持“自下而上拆解 + 自上而下验证”的增量工作流，避免了试图一步到位构建完美知识体系的陷阱，让系统在持续输入中自然收敛。
