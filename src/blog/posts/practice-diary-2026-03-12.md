# 降低模板创作门槛：决策引导与确定性骨架的实战落地

> Day 41 · 2026-03-12

今日的核心任务是将散乱的 Journal 素材转化为可复用的结构化知识，但在处理 `js-knowledge-prism` 的产出流程时，我深刻意识到模板创建的高门槛正成为阻碍团队规模化产出的瓶颈。单纯依赖 CLI 工具无法解决新用户面对 frontmatter、区段结构和变量表时的认知负担，必须引入一套兼顾“决策引导”与“确定性执行”的技能体系。

## 从 CLI 工具到专用技能的范式转移

在复盘 `js-knowledge-prism` 的扩展过程时，我发现模板创建（如 `templates/outputs/prompts/` 下的文件）涉及多层知识，新用户极易在配置细节中迷失。此前我们倾向于提供强大的 CLI，但今天针对 `prism-template-author` 技能的设计讨论让我明确：LLM 的核心价值在于生成高质量的创意内容（如 Prompt 编写），而非仅仅生成空骨架。因此，我们决定放弃仅提供命令行参数的思路，转而设计专用技能，通过 SKILL.md 进行决策引导，将用户从繁琐的结构配置中解放出来，专注于业务意图的表达。

## 三层架构与四问映射的自动化配置

为了解决配置复杂性问题，我将 `prism-template-author` 技能架构定义为“决策引导 + Schema 参考 + Scaffold 工具”的三层设计。核心在于 SKILL.md 中的四个关键问题映射机制：通过询问“产出形态”（如 per-kl 或 per-perspective）、“写作风格”（叙事复盘或结构化教程）、“生成复杂度”（单段或多阶段）以及“质量审校”需求，系统能自动推导出对应的 split、type 和组件配置。这种设计配合 `schema-reference.md` 附件，确保了用户只需回答业务层面的问题，技术细节则由技能内部逻辑自动完成。

## 确定性骨架与 Agent 创意填充的严格分工

在实现 `prism_scaffold_template` 和 `prism_scaffold_component` 这两个 AI 工具时，我坚持了“纯确定性逻辑构建骨架，Agent 负责内容填充”的分工策略。这两个工具被严格限制为不调用 LLM，仅负责校验模板名是否重复、合并 type 默认值、生成标准的 frontmatter 及区段占位符（如 `# Stage:` 或 `# Review Prompt`）。这种职责剥离确保了文件结构的绝对正确性，避免了 LLM 幻觉导致的格式错误，而具体的 Persona 定义或 Style 描述则完全交给 Agent 根据技能引导后的上下文进行高质量填充。

## 渐进式披露策略与标准化路径规范

为了控制认知负荷，我实施了渐进式披露策略，将主技能文件 `SKILL.md` 严格控制在 130 行以内，而将详细的 Frontmatter 字段表、变量表及区段规范移至 `schema-reference.md` 供 Agent 按需查阅。同时，我们规范了文件写入路径：优先写入知识库的 `outputs/_templates/` 目录，若不存在则回退至项目内置目录。生成的模板必须包含标准的 `openclaw-plugin` 目录结构及 `package.json`，确保了产出物的一致性和可维护性，使得新模板能立即融入现有的自动化闭环。

## 基于 Dry-run 的预验证闭环

在模板正式落盘前，建立强制的验证机制是今日的另一项关键决策。我们要求在生成完成后，必须通过 `npx js-knowledge-prism output --dry-run` 命令进行预验证。这一步骤作为自动化闭环中的关键质检点，能够在不污染知识库的前提下，确认新生成模板的逻辑与结构是否符合预期。此外，今日在修复 Draft 机制时区 Bug 的过程中（将 `new Date().toISOString()` 改为本地日期计算），也再次印证了在写入前进行严格逻辑校验的重要性，防止因环境差异导致 `draft: true` 标记失效。

## 今天的收获

- **技能优于纯 CLI**：对于高门槛任务，设计带有决策引导（四问映射）的专用技能比提供复杂 CLI 参数更能释放 LLM 的创意价值。
- **确定性骨架原则**：文件结构生成必须使用纯确定性逻辑（Scaffold 工具），严禁调用 LLM，以确保元数据和区段结构的绝对正确。
- **渐进式披露设计**：主技能文件应保持轻量化（<130 行），将复杂 Schema 置于附件，有效降低 Agent 和用户的首屏认知负荷。
- **非破坏性验证**：在写入生产环境前，强制执行 `--dry-run` 预验证，是保障自动化闭环稳定性的关键质检点。
- **本地日期陷阱**：涉及“当天”判断的逻辑（如 Draft 标记）必须使用本地日期计算，避免 UTC 时区差异导致流程断裂。
