# 逆向架构破局：让 Agent 实时接管用户正在使用的浏览器

> Day -11 · 2026-01-19 · 骨架 [KL27](./KL27-2026-01-19.md)

今天最大的决策是否定了“由 Agent 启动浏览器”的传统路径，转而构建了 JS Eyes 项目，确立了“浏览器主动连接 Agent"的逆向架构。面对主流框架（如 Puppeteer）必须独立启动进程、无法轻量级复用用户当前环境的痛点，我通过浏览器扩展与 WebSocket 服务器的双向链路，成功实现了 Agent 对用户正在使用的 Chrome 和 Firefox 浏览器的低侵入实时控制。

## 填补实时复用环境的架构空白

在梳理 OpenClaw 的浏览器交互需求时，我发现现有的 Agent 框架存在一个明显的盲区：它们擅长控制“新开的”浏览器，却对“用户正在用的”浏览器束手无策。为了解决这个问题，我设计了三层解耦架构：运行在用户端的浏览器扩展（支持 Chrome MV3 和 Firefox MV2）、作为中间层的 Node.js WebSocket 服务器，以及注册在 OpenClaw 中的 Agent 插件。这种设计让浏览器扩展无需感知 Agent 的具体实现，Agent 也不必关心底层浏览器的差异，仅通过 WebSocket 即可建立持久通信。今日 12:49 完成 Initial commit 后，我迅速验证了这一链路，扩展能够自动追踪标签页变化并执行远程指令，真正做到了“所见即所得”的实时接管。

## 跨平台核心能力的闭环与演进

为了确保架构的通用性，我同时适配了 Chrome/Edge（Manifest V3）和 Firefox（Manifest V2），虽然两者的后台脚本生命周期和权限声明存在差异，但我通过独立的代码目录（`chrome-extension/` 与 `firefox-extension/`）实现了功能对等。在 v1.1.0 版本发布前（今日 17:18 完成），我重点打磨了五大核心能力：实时 WebSocket 通信、标签页同步（URL、标题、ID）、远程控制（打开/关闭/获取 HTML）、Cookie 管理以及断线后的指数退避重连机制。特别是在处理跨域内容获取时，我利用 Content Script 注入方案绕过了常规限制。从 v1.1.0 的核心功能闭环，到规划中 v1.2.0 将引入的 HMAC-SHA256 认证，再到 v1.3.x 系列将专注的速率限制与熔断机制，这条“功能→安全→稳定”的演进路径已在今日的代码结构中初具雏形。

## 基于注册表的技能生态自动化

在基础自动化之上，我进一步思考如何让系统具备自我进化的能力。通过在 `openclaw-plugin/` 目录下构建完整的插件，我注册了 9 个 AI 工具，涵盖从 `js_eyes_get_tabs` 到 `js_eyes_execute_script` 的全套操作，并内置了后台服务以支持插件加载时自动启动 WebSocket 服务器。更关键的是，我设计了扩展技能（Extension Skills）系统，以 `js-search-x` 为例，它作为一个独立的 OpenClaw 插件，提供了 `x_search_tweets` 等高层能力。Agent 现在可以通过 `js_eyes_discover_skills` 查询注册表，再调用 `js_eyes_install_skill` 自动完成下载与注册。为了降低部署门槛，我还编写了 `install.sh` 和 `install.ps1` 脚本，支持通过 `curl` 管道或 PowerShell 变量赋值实现一键安装，彻底打通了从技能发现到落地的最后一公里。

## 今天的收获

- **逆向架构价值**：在 Agent 与浏览器交互场景中，“浏览器主动连接”比"Agent 启动浏览器”更能满足实时复用用户环境的轻量级需求。
- **分层解耦策略**：通过“扩展 - 服务器 - 插件”三层架构，有效隔离了浏览器内核差异（MV2/MV3）与 Agent 框架逻辑，提升了系统的可维护性。
- **演进路径规划**：明确“核心功能→安全认证→稳定性增强→生态扩展”的版本迭代顺序，避免在早期过度设计安全或治理模块。
- **自动化部署闭环**：利用 OpenClaw 插件注册表机制配合一键安装脚本，实现了技能生态的自动发现、安装与热加载，减少了人工干预。
